# The data architecture behind a verified ping

**Reference, not rationale. Verified against `6373630` (2026-09-11).**

[ROUTER.md](ROUTER.md) says *why*. This says *what*: every field that goes
over the wire, in order, with real bytes rather than invented ones. Every
value below was generated by the running code.

A ping is the whole mechanism with the payload taken out, which is why it
is the thing worth explaining first: everything else is this, carrying
something.

---

## 1. The cast

**Bert** wants to ask **John** something. Neither can reach the other
directly — they are both behind home routers — so everything goes through
a **relay** they both have a row on.

Three facts that make the rest make sense:

- **Bert and John are public keys**, not names. Two people can both be
  called "john"; two keys cannot both be the same key.
- **John's node is already connected** to the relay and holding a stream
  open. Nothing can be sent to somebody who is not there, and the relay
  says so instantly rather than waiting.
- **The relay can read everything** and can change nothing without being
  caught. That is the whole trick, and §6 is how.

## 2. The four things that travel

```
  Bert's node  ──①POST /api/relay/post──▶  relay
                                             │
                                             ②"request" down John's open stream
                                             ▼
                                          John's node
                                             │
  relay  ◀──③POST /api/relay/reply──────────┘
    │
    ④"reply" down Bert's open stream
    ▼
  Bert's node
```

Two ordinary POSTs, two events on streams that were already open. **No
connection is ever held waiting.** Each POST answers at once and says only
whether it was accepted.

## 3. ① What Bert posts

```
POST /api/relay/post
Content-Type: application/json

{
  "from": "MCowBQYDK2VwAyEA/BOqOD5to2feQNRbeJK+w1rfq80XdbL4rWzR6f0Zhf8=",
  "to":   "MCowBQYDK2VwAyEA32cX+eQRxw1DeesDQzpZGKCKkMuNCIXvjYoGTn6+A+0=",
  "text": "{\"app\":\"ping\",\"v\":1,\"id\":\"9f3c1a7e5b2d4680c1e8a3f70d5b9264\",\"body\":{}}",
  "sig":  "ySQ6mCzZAzTJcmnvDzpOH8VFcVx3RPvMK2hP7J8uUfVp+ee7eyR9w9zmzKYiZv/EXWxH/b0bSzfPo7HnAIcnDQ=="
}
```

| field | what it is |
|---|---|
| `from` | Bert's public key. Who is asking. |
| `to` | John's public key. Who is being asked. |
| `text` | The message itself, **as a string**. The relay never opens it. |
| `sig` | Bert's signature. §4 says over what. |

**`text` is a string, not an object, and that is deliberate.** Inside it is
an envelope the apps agree on — `app`, `v`, `id`, `body` — and the relay
has never been taught what any of that means. It carries a string. If the
apps invent a new field tomorrow, no relay anywhere needs updating.

The `id` inside is 32 hex characters of **cryptographic randomness**, made
fresh for this one send. It is what makes this request unlike any other
request ever made, which matters in §5.

**The relay answers immediately:**

```
202  { "ok": true, "status": 202, "hash": "d6ad958a…" }
```

or one of:

| | |
|---|---|
| `403` | the signature is not Bert's, or Bert has no row here |
| `404` | nobody on this relay holds that `to` key |
| `503` | John is not connected — **not reachable right now** |
| `409` | *already in flight* — this exact request is still going. **Wait, do not resend.** |
| `429` | Bert has too many requests open at once |
| `413` | `text` is over 16 KB |

## 4. What Bert signed, and why it looks like that

Signatures here are never over an object. They are over **a string built to
a recipe**, because two honest programs can disagree about how to flatten
an object into bytes — key order, spacing, how numbers are written — and
then a perfectly good signature fails for a reason nobody can see.

The recipe, with real newlines where `\n` appears:

```
post
MCowBQYDK2VwAyEA/BOqOD5to2feQNRbeJK+w1rfq80XdbL4rWzR6f0Zhf8=
MCowBQYDK2VwAyEA32cX+eQRxw1DeesDQzpZGKCKkMuNCIXvjYoGTn6+A+0=
29818950
{"app":"ping","v":1,"id":"9f3c1a7e5b2d4680c1e8a3f70d5b9264","body":{}}
```

Five lines: **the word `post`**, then from, then to, then a number, then
the text.

- **The word `post`** is there so this signature cannot be reused as
  anything else. Bert signs other things all day — reading his inbox,
  opening his stream — and none of those signatures may be spendable as
  "send this to John".
- **`29818950` is the minute**, counted from 1970. Not the second — the
  minute — so two clocks a little out of step still agree. A signature is
  accepted for the minute before, the minute itself, and the minute after,
  and is worthless three minutes later.

## 5. The hash: the name of this request

Take the five-line string above, run SHA-256 over it, write it in hex:

```
d6ad958af9c46e9b3939a805efb759371f22ceffa45c7eff801340b2861935d8
```

That is this request's name, everywhere, at every hop, for its whole life.

**A hash is a one-way fingerprint of a stream of bytes.** Same bytes in,
same fingerprint out, always; change one character and it is completely
different; and you cannot work backwards from the fingerprint to the bytes.

Three things make it the right name:

**It is the fingerprint of exactly what was signed.** Not of the object,
not of the POST body — of the five lines. So there is never a question
about what it covers.

**It cannot collide by accident**, because those five lines contain the
32-hex-character random `id` from §3. Two different requests cannot be the
same bytes.

**It cannot collide on purpose either**, because the five lines also
contain `from`. Two *different people* can never produce the same hash,
however hard they try.

> **A hash says "these are the bytes". It does not say who.** Anybody can
> run SHA-256. That is why knowing a hash never grants anything — see §7.

## 6. ② What John's node receives

```
event: request
data: {"from":"MCow…Zhf8=","to":"MCow…+A+0=",
       "text":"{\"app\":\"ping\",…}","sig":"ySQ6mCzZ…"}
```

The same four fields Bert posted, passed through unopened.

**Notice what is missing: the hash is not here.** The relay knows it, and
deliberately does not send it. John's node works it out for itself, from
the bytes it just received, by rebuilding the five lines of §4.

That one omission is the heart of the design:

- If the relay *sent* the hash and John *echoed it back*, the echo would
  prove nothing — John could have been handed anything.
- Because John computes it from bytes he actually holds, his hash matching
  Bert's is **proof that the bytes arrived unchanged**.

So if the relay altered the request in flight, John's five lines differ,
his hash differs — and in fact Bert's signature would not even verify. The
tampering is caught by arithmetic, with nothing in the system having to go
looking for it.

**And John does not need the minute either.** He tries the three candidate
minutes and keeps whichever one makes Bert's signature verify. The number
never travels; it is *recovered*. Both ends end up holding the identical
five lines without ever having discussed which minute it was.

## 7. ③ What John's node posts back

```
POST /api/relay/reply

{
  "from": "MCowBQYDK2VwAyEA32cX+eQRxw1DeesDQzpZGKCKkMuNCIXvjYoGTn6+A+0=",
  "hash": "d6ad958af9c46e9b3939a805efb759371f22ceffa45c7eff801340b2861935d8",
  "text": "",
  "sig":  "IHhqwnJG2dvmAeRul2J12Pif6sPibBMSZ3lSXaLciwpkZAE2G0RPNuF/NqBO80HMqCRSo6Er1859SonAxa40AQ=="
}
```

Signed over three lines:

```
receipt
d6ad958af9c46e9b3939a805efb759371f22ceffa45c7eff801340b2861935d8
29818950
```

**The hash is INSIDE the signed message, not merely next to it.** If it
travelled alongside a signature over something else, the relay could swap
it for a different hash and nobody would notice. Inside, it cannot.

**The relay then makes two checks, and they are not the same check:**

1. Is there a request waiting under this hash? — *finds* the request.
2. Is the poster the person that request was addressed to? — *permits* the
   answer.

Only the second is permission. Anybody who saw the bytes could compute the
hash, so if the hash alone were enough, anyone who overheard a request
could answer it.

## 8. ④ What Bert gets back

```
event: reply
data: {"hash":"d6ad958a…","from":"MCow…+A+0=","text":"","sig":"IHhqwnJG…"}
```

Here the hash **is** sent, and that is fine — Bert is not taking anybody's
word for it. He:

1. looks up the hash in his own list of requests he is waiting on,
2. checks the signature against **John's public key**, which he already has
   from the relay's public member list.

If both hold, Bert knows **John's node received exactly the bytes Bert
sent**. Not the relay's word for it. John's.

## 9. A receipt is not a reply

A receipt says *"this arrived."* It does not say a human read it, and it
does not carry an answer.

That distinction is forced by something true about the system: **a node is
always up; an app is not.** John's node holds its connection around the
clock, so it can always sign "received". The app that would *compose* an
answer is a browser tab that may be closed.

So a request gets **two responses at different times**:

- **The receipt**, at once, from John's *node*. Always available.
- **The answer**, later and only if somebody is home, as its own message
  carrying the same hash.

A receipt is simply the answer a node gives when nobody is home. Both
travel identically; only `text` differs.

## 10. What is deliberately NOT here

| missing | why |
|---|---|
| the hash, on the way out | John must derive it, or it proves nothing (§6) |
| the minute, anywhere | recovered from whichever makes the signature verify (§6) |
| any signature by the relay | the relay is not a party; it carries and cannot vouch |
| the message, on disk | the relay stores nothing it routes |
| encryption | **the relay reads everything.** It cannot lie about what it read, but it can read it |

That last row is the honest limit and the one most easily misread.
Untamperable is not private.

## 11. The promise this adds up to

> **You may be told it failed when it arrived. You can never be told it
> arrived when it did not.**

Because a receipt is signed by the recipient, nothing in the middle can
manufacture one. The worst that happens is Bert times out while John
actually got it — a false alarm, never a false comfort.

## 12. Good questions to ask of this

Written down because they are the ones worth arguing about, not because
they are answered:

- If the same request is sent twice on purpose — a real retry after a
  timeout — the hash is the same. The relay says *already in flight* while
  the first is alive, and treats it as new after it expires. **Is
  20 seconds the right life for a pending request?**
- 16 KB is the cap on `text`. **Is that an API call or a chat message?**
  It decides how much memory a busy relay holds at once.
- A node can answer only requests it was awake for. **Should it be able to
  answer one it missed**, and would the asker still care by then?
- Bert learns John's node received the bytes. **He learns nothing about
  whether John will ever act on them.** Is that the right place for the
  guarantee to stop?
- Everything here is readable by the relay. **Which traffic, if any,
  should not be** — and is that a new arc or a change to this one?
